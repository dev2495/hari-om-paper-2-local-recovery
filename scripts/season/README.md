The fresh-start reset archives and clears operational testing records from both plants. It retains users, security history, master data, numbering counters, material QC templates, seasonal rule history and plant configuration. Physical stock, tool assets, procurement, dispatch, sales, specs, job cards, accounting reconciliation and pending integration/outbox records are cleared together. New imports must be deliberate after restart.

1. Review the dry-run manifest against the intended seven databases and exact table classification.
2. Stop the entire application runtime, schedulers and workers. Keep PostgreSQL running. The apply command refuses any remaining database client pools.
3. Run the same script with the reviewed archive directory and reset ID, `--apply` and `--confirm 'ALL CURRENT OPERATIONS ARE TEST DATA'`. Supply DB settings through the environment; do not put credentials in command text.
4. All seven full dumps are checksum-verified, restored into disposable databases and checked by table counts and content hashes before any operational table is cleared. Apply compares the reviewed preview counts and content to the stopped runtime. Drift requires a new reviewed preview. There is no TRUNCATE CASCADE. Unclassified tables outside the retained authentication/security catalogue, or retained dependencies, stop the operation. Authentication retains its catalogue except the two explicitly classified notification tables.
5. Inspect `reset-manifest.json`. Keep the app offline after any partial failure. Recover every database with the same archive/reset ID, `--restore --confirm 'RESTORE ALL SEVEN DATABASES FROM THIS BACKUP'`. Recovery verifies all seven dump checksums before starting and uses a transaction per database, then verifies archived counts and content. Never bring up a partially recovered runtime. Preview cannot replace a recovery manifest; later previews require a fresh archive and reset ID. Manifest checkpoints are written atomically. A COMPLETE archive is idempotent and never deletes newly entered records on rerun.
6. Restart and verify the Owner, QC, Sales, Planner and shop-floor workflows. Number counters retain their history. Confirm both seasonal published rules and the active season before creating new specifications.

This runner is offline administrative tooling, never a browser button. The deployed image and before/after backup IDs must be included in the release evidence.

The AWS wrapper holds both release and backup locks. It durably records the original timer states in `maintenance-state.json` before stopping them. Failed reset/recovery/readiness leaves the app and timers offline; a successful retry or restore reuses the original schedules, including a deliberately paused timer. A completed and resumed reset replay does not restart the app or change later timer preferences.

If the legacy material-routing guard requires a reset before deployment, stage only the reviewed reset Python file under `/opt/hariom/` and supply `ERP_RESET_SCRIPT` plus its exact `ERP_RESET_SCRIPT_SHA256` to the wrapper. Overrides must be absolute regular files and match the supplied checksum. The wrapper still checks the actual deployed commit; never overwrite live source or change its marker to make a pre-deploy reset work.

Release holds the backup lock through build, cutover and rollback. Nested backups validate their inherited FD9 and record the exact S3 key and archive SHA-256. Release acceptance restores that specific post-activation archive, rather than selecting a possibly unrelated newest object. Original timer states remain available in the release evidence if manual recovery is needed.

Focused offline safety tests: `python -m pytest scripts/season/tests/test_release_reset_safety.py -q`. These exercise fake AWS/Docker/systemd tools and real OS file locks; they do not prove deployed AWS readiness or contact any database.
